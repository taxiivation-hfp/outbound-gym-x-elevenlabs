## What we are being scored on

Preliminary round, 80 points, judged from the public repo, a live production
URL and a 3–5 minute demo video. Finals, 20 points, live pitch.

The parts of the rubric this plan is built to hit:

| Criterion | Pts | What earns top marks | What we build for it |
|---|---|---|---|
| Functionality & Execution | 10 | Fully working, live app not localhost, handles edge cases, no visible bugs | Phases 1–3, deployed |
| Technical Difficulty | 8 | Agentic/multi-step reasoning, **custom evaluation**, model chaining | Phase 4 eval harness, Phase 6 closed loop |
| Code Quality & Architecture | 6 | Clean, modular, documented, team can justify choices | Phase 7 README |
| Use of Data / Models | 6 | Model choice justified on cost/latency/accuracy, **some form of evaluation** | Phase 4 + Phase 7 |
| Feasibility & Viability | 8 | Costs, data access and constraints acknowledged honestly | Phase 7 |
| Impact & Value Proposition | 9 | Specific, semi-quantified value | Phase 5 churn intelligence |

Two consequences to internalise:

**A broken feature scores worse than an absent one.** The 0–4 band is "breaks
during the demo video". Three call types that all work beats five that
sometimes work.

**Honesty about limitations scores.** The 7–8 functionality band is "minor
rough edges or known limitations the team is upfront about", and the finals
Q&A criterion explicitly rewards being "honest about limitations when pressed".
Do not paper over gaps. Document them.

## Phase 1 — Make the data support the product

Nothing else can be tested until this is done.

1. **Add `auto_renew` to `generate_gym_data.py`.** Roughly 25–30% of members,
   true. These members are never called. This is the product's core rule and
   its best pitch line, so it must be visible on the dashboard, not merely
   enforced in a filter.
2. **Stop dropping fields in `build_scores.py`.** Emit per member: raw ISO
   `expiry_date` for every member (not just winback), `auto_renew`,
   `contract_type`, `monthly_fee`, `days_since_visit`, `old_rate`,
   `tenure_days`, `visit_count_90d`.
3. **Widen the expiry windows so all three call types have members.**
   Currently zero members can trigger renewal, and zero are expired long
   enough for the 3-month or 6-month winback windows. Target roughly 15–25
   members in each of: renewal, reengagement-early, reengagement-near-expiry,
   winback 1-month, winback 3-month, winback 6-month. Exact counts don't
   matter; non-zero does.
4. Treat `month-to-month` as auto-renew, `6-month` and `12-month` as
   fixed-term. If that skews the distribution badly, set `auto_renew`
   independently instead — it is synthetic data, make it serve the demo.
5. **Retire the 90.4% cohort-accuracy claim.** It was measured against an
   answer key generated by the same rules being evaluated, which is circular
   and will not survive Q&A from a judge with a statistics PhD. Remove it from
   anything judges see. Phase 4 replaces it with real evaluation. Note the
   removal in your report.

## Phase 2 — Wire the three agents

6. **Derive `call_type`** per member: `"renewal" | "reengagement" | "winback"
   | null`. Keep the framework's `cohort` field untouched and
   `channel: "ai_call"` as-is; `call_type` is a new field beside them.
   Triggers per `charlie_build_brief.md`, plus one addition: only fire the
   reengagement absence trigger when the member had an established habit
   (`old_rate >= 1.0`). Without that guard, sporadic attenders flood the queue.
7. **Hard filter.** `auto_renew == true` → `call_type = null`, never queued,
   and `/api/call` returns 403. Reuse the framework's existing 403 pattern;
   change what it checks to `auto_renew == false && call_type != null &&
   !do_not_contact`.
8. **Three agents in ElevenLabs**, prompts pasted literally from
   `charlie_build_brief.md`. Three env vars, route picks the agent by
   `call_type`. Apply the settings in the brief's Step 3, and record the
   reasoning for each — Flash v2.5 for latency, mu-law 8000 for telephony,
   temperature 0.3 — because Use of Data / Models is scored on exactly that.
9. **One translation layer**, `lib/compileVariables.ts`. Framework names stay
   everywhere inside the app; Charlie's names appear once, where the route
   builds `dynamic_variables` and where the webhook reads
   `data_collection_results`. Compile `context`, `expiry_line`, `time_left`
   and first-name-only `member_name` here, at call time — not in Python. The
   Python pipeline's clock is frozen at 2026-09-12, so anything compiled
   offline will be wrong on stage.
10. **Fix these three bugs in the brief while transcribing.** They are defects
    in the brief, not the framework:
    - Winback prompt reads "Their membership expired `{{time_left}}`" while the
      example value is "expired three weeks ago". Drop "expired" from one side.
    - The month-or-less `expiry_line` block contains a literal `{{time_left}}`.
      ElevenLabs does not expand placeholders inside a variable's value, so the
      compiler must substitute it.
    - Only one `context` template exists, for an absent member. Write the
      renewal and winback versions.
11. **Gym config** in a checked-in `data/gyms.json` holding **two** gyms with
    different incentives, hours and locations, switchable from the dashboard.
    `GYM_NAME` env var goes away. Two gyms rather than one because "one agent,
    config per gym" is the scalability claim, and switching live proves it
    instead of asserting it.

## Phase 4 — The eval harness (highest technical value here)

The rubric names "custom evaluation" as a top-band signal for Technical
Difficulty, and "some form of evaluation" for Use of Data / Models. This is the
single highest-scoring item in this document. Build it properly.

17. **Turn the brief's 15 verification scenarios into an automated suite.**
    Each scenario is a named test with a fixed set of dynamic variables, a
    scripted member persona, and an explicit pass condition. Use ElevenLabs'
    conversation simulation if the API exposes it; otherwise drive the member
    side with an LLM given the persona and run the agent against it.
18. **Every scenario needs a machine-checkable assertion.** Not "did it sound
    good" — "did the agent state the price before being asked", "did it mention
    time remaining when `expiry_line` forbade it", "did it make a second ask
    after a refusal". Assertions can be string checks or an LLM judge handed
    the transcript and the single rule under test. Prefer whichever is cheaper
    and works.
19. **Run it, store results, show them.** An `evals/` directory with scenario
    definitions, a runner, and committed output. Then a dashboard page showing
    pass rate per agent per scenario. A judge reading the repo should find this
    without being told.
20. **Report the failures too.** A suite passing 15/15 first try looks
    fabricated. When scenarios fail, fix the prompt and keep both runs. The
    delta is the evidence of engineering.

## Phase 5 — Churn intelligence

What turns a dialer into a product, and where Impact & Value is won.

21. **Aggregate `reason_for_absence` across completed calls** into a view: why
    members leave, broken down by cohort, call type and tenure band. No
    competitor captures this — they capture *that* someone churned, not *why*,
    in the member's own words.
22. **Surface `committed_day`** as an operational output: who told Charlie
    they're coming in and when, so the front desk can expect them.
23. **A cost-and-value panel.** Cost per call from ElevenLabs pricing against
    the value of a retained member, computed from `monthly_fee` and tenure.
    Rough is fine; the rubric asks for "at least semi-quantified". Put the
    assumptions on screen so they're auditable.

## Phase 6 — The closed loop

24. **Feed post-call analysis back into the next call.** A member whose first
    call extracted `reason_for_absence = "injury"` gets different `context` on
    the next call, and Charlie does not re-ask a question already answered.
    This is genuine multi-step agentic behaviour rather than a one-shot API
    call, and it solves the "half-worked call" problem deferred in
    `charlie_spec.md`.
25. **Real `attempt_number` tracking** from `call_records`, per the spec: which
    conversation this is, not which dial; a no-answer does not increment it.
    Unlocks the "noticeably briefer on attempt 2" behaviour, worth demoing.
26. **`do_not_contact` persisted and enforced** in the same 403 branch as the
    auto-renew filter. Permanent, honoured across all call types.
27. **Escalating cooldown.** Ring on the absence trigger, then leave the member
    alone for three months if nothing changed. If the call did get them in —
    even once — the normal trigger resumes. Router logic only, no prompt change.

## Phase 7 — The repo as a scored artifact

Six points for Code Quality & Architecture and eight for Feasibility are
awarded from reading the repo. Write for that reader.

28. **README** covering the problem with a named target customer, how to run
    it, the architecture, and a decisions section explaining *why* — the top
    band is "the team clearly understands the why behind their architecture
    choices". Worth explaining:
    - Why three narrow agents instead of one with `call_type` branching — a
      branching prompt lets the agent drift into the wrong track mid-call.
    - Why prompt variables are compiled plain-English strings rather than
      conditionals in the prompt — the gym's rules change, the prompt doesn't.
    - Why variables compile at call time, not in the pipeline — frozen clock.
    - Why the router is rule-based and interpretable rather than a churn model.
      A front-desk manager has to see why a member was called. This is a
      deliberate trade against raw accuracy and a differentiator against
      black-box churn scores.
    - Why auto-renewing members are never called.
    - Model and audio-format choices, with the latency and cost reasoning.
29. **A LIMITATIONS section, honest and specific.** Synthetic data, so the
    router is validated in structure but not in accuracy. No real gym
    integration. Single test phone number. No voicemail handling. What real
    deployment needs: which fields from which gym management systems (Glofox,
    Mindbody, PushPress export shapes), consent and telemarketing obligations
    under Australian law, per-call cost at volume.
30. **Architecture diagram.** One image, in the README.

## Frontend

**Do not touch it during Phases 1–6.** It needs one dedicated pass afterwards
covering structure and aesthetic together — restyling before the merge lands
means doing it twice.

That pass must show: three call types, not "Winback Call Transcripts"; an
excluded-members bucket with the reason stated; the ten `outcome` values
instead of the framework's three; the eval results page; and the churn
intelligence view. `lib/types.ts` and `TranscriptPanel.tsx` label and style
maps both need widening.

## Do not

- Do not merge the three agents into one with `call_type` branching. It looks
  like duplication and is a deliberate decision.
- Do not build a path that calls an auto-renewing member.
- Do not compile prompt variables in Python.
- Do not rename the framework's `cohort` values or reorder its buckets.
- Do not bolt on RAG, a vector store or a fine-tune to chase Technical
  Difficulty points. The rubric penalises AI that feels bolted on under
  Creativity, and the honest depth here is the eval harness, the closed loop
  and the prompt architecture. Build those instead.
- Do not restore the `first_message` override requirement from the brief. It
  was specified without a use case. Ignore it.
